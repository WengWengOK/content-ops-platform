# 内容运营平台（ContentOps）— STAR 描述

> 一句话：把「选题 → 内容 → 配图 → 发布 → 评论运营 → 数据复盘」做成一条可编排、可打断、可观测、
> 成本可控的 AI 流水线，而不是几个孤立的 Prompt 演示。

---

## 一、S — Situation（背景与痛点）

内容创作者和小团队的日常是这样的：

1. **选题靠刷**：热点散在微博/知乎/抖音/B站，人工刷完热点已经凉了；
2. **写作靠憋**：同一个主题，小红书要口语化短句、公众号要结构化长文，一稿多投效果差；
3. **配图靠找**：文字与封面风格不统一，图文作品排版要手工；
4. **发布后全丢**：评论没人回、差评没人管、数据没人复盘，账号收益靠玄学。

而"套壳 LLM 应用"的三个通病在这里同样致命：**成本不可控、质量不可测、幻觉不可查**，
再叠加多租户下的**数据隔离与凭据安全**问题。

---

## 二、T — Task（目标）

1. **可编排的流水线**：4 阶段（选题/内容/配图/发布）按阶段出产物，选定多平台时并行扇出；
2. **人在环上**：选题、平台、大纲、风格由用户判断；能打断、能对话续改；产出可下载、可可视化编辑；
3. **发布后闭环**：评论采集 → 意图识别 → 场景客服起草 → **忠实度校验（只标记不修正）** → 人工复核 → 真实回复；
4. **工程标准对齐大厂**：分布式追踪与指标、LLM 评测门禁、成本熔断与预算、JWT + RBAC + 租户隔离、
   凭据加密与密钥轮换、操作审计。

---

## 三、A — Action（做了什么）

| 模块 | 关键实现 | 可验证的东西 |
|------|----------|--------------|
| 编排 | `PipelineOrchestrator` 状态机 + 人工确认节点 + 崩溃恢复 + 事件 Outbox（Kafka 就绪） | 阶段产物、人为确认后继续、重启不丢流程 |
| 多平台 | `PlatformCode` 用 1 字节存平台、按平台出产物、ZIP 打包下载 | 同一份内容出小红书/公众号/抖音/B站不同形态 |
| RAG 检索 | 文档摄入（PGVector + 本地 BGE 嵌入，无外部 Key）→ BM25 混合检索 → 重排 → HyDE/Multi-query → RAGAS 评测 | 检索链路可诊断（storeMode/索引大小/评测对比） |
| 知识库问答 + 错误识别 | 检索充分性 → 接地生成 → 引用校验 → 忠实度校验 → 隐式信号归因 → 离线聚类与回归 | 五层信号落库，见 [RAG-ERROR-DETECTION.md](RAG-ERROR-DETECTION.md) |
| 评论助手 | 采集（自建桥 / 通知增量）、意图语料库 RAG 前置、关系标签（粉丝/关注/好友/常客/路人）、附件（图/视频）与归属、场景客服 Agent、复核状态机 | 采集→分析→起草→审核→真实回复全链路 |
| 场景客服 Agent | 可插拔 profile（电商带货 / 课程模板 / 通用客服）+ 禁止承诺/未核实价格/漏提示转人工等校验，**只标记不修正** | 新场景不改代码，配置即生效 |
| 热点监控 | 7 平台热榜多路降级、关键词启停与命中、AI 相关性/真假/摘要、突发热点检测、趋势曲线、时间范围筛选 | 热点可直接进选题 |
| 作品与合集 | 作品带平台标签、按类型的合集管理、租户隔离、聊天与作品的所属关系 | 一个作品带完整对话，可继续改 |
| 可观测 | OTel 分布式追踪（Jaeger）、LLM token/成本/延迟大盘（Prometheus + Grafana）、LLM trace 表、Grafana Alerting → 飞书/企微 | 一条告警链路端到端可跑 |
| 治理与安全 | JWT + RBAC（ADMIN/CREATOR/VIEWER）、凭据 AES-GCM 加密 + 掩码出参 + 密钥轮换、操作审计、安全护栏、成本熔断与预算告警 | 跨租户访问 403、凭据永不回显明文 |
| 工程质量 | 后端 **449 个测试全绿**、CI（后端测试 + 前端构建 + LLM 评测门禁阈值 70） | 改动有回归保护 |

## 四、R — Result（结果）

**1）跑得通的闭环，不是纸面能力。** 以本轮知识库问答为例，端到端实测（本地真实模型 + 真实检索）：

- 能答的问题：覆盖率 0.936 → `SUPPORTED` → `risk=NONE`，引用合法；
- 答不了的问题：模型拒答 → 记 `MODEL_REFUSED`（知识库盲区）→ `MEDIUM`/抽样；
- 追问质疑：`DOUBT_REPHRASE` → 上一条问答自动打 `suspected_error`；
- 编造答案（人工改写后复检）：覆盖率 0.216 + 引用 `[9]` 越界 → `HIGH` → 进复核清单，**答案文本一字未改**；
- 离线：拒答问题聚成 2 个盲区簇；错误样本一键并入评测集（stage=`kb-qa`）做回归。

**2）成本与质量同时被压住。** 阶段级模型分层 + maxTokens 上限 + 默认关闭自动重试 + 成本熔断与预算 80% 告警，
全档低价模型下单工作流成本约 **¥0.03 量级**；full-image 等高价值作品才用更贵的档位。

**3）误判率是"量化在改"的，不是嘴上说的。** 本轮实测抓出并修掉两个真实误判（长证据 + 短结论用 Jaccard 把正确的判成编造；
模型主动拒答被当成引用不实），两个都补了回归单测。

**4）可运维。** 一次问答带齐四类错误的判定结果 —— 高置信度进人工清单、中低置信度抽样、
低置信度样本离线聚类找盲区、攒够了再训小分类器。

## 五、多智能体框架选型：CrewAI 在本项目的位置

**现状**：编排是**Java 侧的确定性状态机**（`PipelineOrchestrator` + 人工确认节点 + 成本熔断 + 崩溃恢复），
Agent 用 LangChain4j 实现，对外已经暴露 **MCP Server（`/mcp`）** 和 **A2A 事件契约**。

**CrewAI 是什么**：Python 多智能体框架，核心抽象是 role / goal / backstory + crew + task 委派，
支持 sequential / hierarchical 两种过程。它的强项是**探索型、多角色协作**的任务。

### 可以接进来的三个位置（按推荐度排序）

| 位置 | 做法 | 为什么合适 |
|------|------|------------|
| 1. 外部研究 crew，用 MCP 挂我们的工具 | CrewAI 侧作为 MCP client 调我们的工具（热点监控、知识库检索、评论采集、全网搜索），产出一份调研/选题报告后回写 | 不改主链路、不引入 Python 依赖到核心服务；工具的鉴权/限流/成本统计仍在 Java 侧统管 |
| 2. 把 crew 包成一个工具 | 把某个 crew（如"竞品调研 crew"）包装成 HTTP 服务或 MCP tool（`research_crew`），由我们的 Agent 按需调用 | 保留 CrewAI 的多角色协作优势，但调用点是显式、可计费、可熔断的 |
| 3. 纯离线 PoC | 独立跑一个 crew 做选题研究/长文写作，用我们现有的评测集（`contentops_llm_eval_case`，含 `kb-qa` stage）对比质量与成本 | 零风险验证收益，再决定是否上主链路 |

### 不建议的做法

- **不要把 4 阶段流水线重写成 CrewAI**。主链路要的是确定性（阶段产物可复现、幂等、崩溃可恢复）、
  人工确认（当前是服务内事务 + 状态机）、成本熔断与预算（按工作流记账）、以及 Java 侧的 OTel/Prometheus 可观测 ——
  这些在自治的多智能体循环里都更难保证；`while` 式自主委派还会放大 token 与不可预测性。
- **不要让它直连数据库**。让它走 MCP/A2A 接口，数据面留在 Java 侧，租户隔离与凭据加密不用重做一遍。

### 真要落地的最小步骤

1. 用 Docker 起一个 Python 服务（CrewAI + 一个 `research` crew），只依赖我们 MCP Server 暴露的只读工具；
2. 给这个服务加一个内部 token，走现有 `AuthFilter`（按租户限流、计费）；
3. 产出物写回：选题候选写 `contentops_topic_*`，调研报告走知识库 `ingest`（自动进 RAG 与评测面）；
4. 跑一轮评测对比（质量分 / 单任务成本 / 时延），达标再决定是否接进工作流的"选题研究"节点。

一句话结论：**CrewAI 适合做这条流水线的"研究外挂"和离线实验台，不适合取代它的编排内核。**
